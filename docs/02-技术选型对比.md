## 三、逐项理由

### A（推荐）：零构建静态 Web App

**为什么强**
- **分发成本几乎为零**：整个文件夹打个 zip 丢微信给朋友，对方解压双击 `index.html` 就能用。不需要 Node、不需要 Python、不需要装包。这是唯一匹配你"直接发文件给别人用"的形态。
- **`file://` 下 ClipboardItem 可用**：本轮受控实验（Playwright + Chromium）里，走 `file://` 协议点击复制按钮，剪贴板拿来是 **94,216 字节、0 处污染**；同一份文件手动 Ctrl+A/Ctrl+C 则是 **125,177 字节、570 处污染、flex 被抹光**。这条已经实测过，不是推测。
- **所见即所得**：左边贴 md、右边实时出效果、主题下拉秒切换，调主题的效率比改模板文件高一个量级。
- **未来能直接上线**：同一份静态产物丢 GitHub Pages / Vercel 就是网页版，代码零改动。

**代价**
- 需要自己写 Markdown 解析与渲染（不能靠 LLM）。但这是**优点**：确定性 + 零成本。
- 纯静态没有服务端，"上传图片到素材库"这类要调微信接口的能力做不了（本期本来也不需要）。

### B / C：命令行 CLI

**优点**：可批处理、好接自动化、容易做 `inspect` 之类的检查。

**为什么不优先**：朋友拿到要么装 Node 要么装 Python，跟"发个文件就能用"直接冲突。md2wechat 走这条路是因为它要靠 CLI 收 API Key 做鉴权——**我们不需要鉴权，就没必要承受这个上手成本**。

> 但 CLI **值得留作第二阶段**：等 Web App 稳定了，把 `engine/` 抽成一个纯 JS 模块，Node 侧包一层 CLI 是半天的事。所以现在目录结构里 `engine/` 是独立的，就是为了将来能复用。

### D：Agent Skill（现状）

**优点**：语义理解强——自动挑选合适的 Component、挑关键词加下划线，这是我们现阶段独有的能力。

**为什么不作为主力**
- **输出不确定**：同样的 md 今天明天出来的可能不一样，不适合"发给朋友当工具用"。
- **朋友必须有 Agent 环境**（Claude Code / CodeBuddy + 订阅）。
- 每篇有 token 成本。

**但要保留**：作为**可选增强层**（方案 E）——用它做"把一篇 md 润色成更适合公众号的结构 / 挑关键词"，再由 A 做确定性渲染。

### E：混合

推荐**长期形态**，但**不要一开始就做**。先把 A 的核心闭环跑通，D 这条链已经存在（gzh-design skill），随时能接。

## 四、关键技术点决策

### 1. 要不要构建工具（Vite / Rollup）？

**建议：不要。**

| | 零构建 | Vite + React |
| -- | -- | -- |
| 发给朋友 | 直接跑 | 要先 build，或用 CDN |
| 改一行代码 | 刷新即可 | 要跑 dev server |
| 依赖体积 | 只 vendor 一个 md 解析器 | node_modules 上百 MB |

代价是不能用 React/JSX——但**这个 App 只有三个控件**（文本框、下拉框、按钮），原生 JS 完全够，反而更轻。

### 2. Markdown 解析器

| 库 | 体积 | 特点 |
| -- | -- | -- |
| **marked** | ~40KB | 小而快，足以覆盖公众号场景 |
| markdown-it | ~100KB | 规范更严格、插件生态好 |
| 自己写 | 0 | ❌ 不划算，表格/嵌套列表/代码块容易出 bug |

**建议 `marked`**，vendor 到本地（`app/vendor/`），**绝不走 CDN** —— 断网也要能用，且加载更快不受墙影响。

### 3. 主题怎么表达？

这是最关键的一步。当前资产是 **md 文档形态**（人读的自然语言规范），新引擎需要**机器能执行的定义**。

**建议：JSON 主题包**，结构草案见 `docs/04-主题开发规范.md`，核心是：

```jsonc
{
  "id": "blue-editorial",
  "name": "科技刊读风",
  "tokens": { "accent": "#2563eb", "border": "#dbeafe", ... },
  "base": { "fontSize": "15px", "lineHeight": 1.95, "align": "justify", ... },
  "components": {
    "lead":     { "from": "blockquote", "tpl": "<section ...>{{content}}</section>" },
    "keypoint": { "from": "h2", "tpl": "..." },
    ...
  },
  "rules": { "maxGradient135": 0, "allowFlex": true }
}
```

三层都要有，**这也是我们相对 md2wechat 的结构优势**：
- `tokens` 决定颜色 → 换色即换皮
- `components` 决定骨架 → 换一套模板即换结构
- `rules` 带着体检阈值 → 主题自带防呆，`maxGradient135` 这种直接从本轮教训固化进去

### 4. 渲染在哪执行？

**必须本地。** 理由：md2wechat 的商业模式就是把渲染放云端然后按 ¥199 收费；我们**渲染放本地 = 天然零成本、可离线、不受它改版影响**。这也决定了纯 JS 引擎是正确选择（浏览器 / Node 都能跑同一份代码）。

## 五、推荐路线

```
第 1 步  MVP（建议这步先做，预计 1–2 轮迭代）
         app/index.html + marked + engine/render.js
         主题：blue-editorial（从本轮已跑通的 v5 成品倒推）
         能力：粘贴 md → 实时预览 → 主题切换 → 干净复制 → 导出 HTML

第 2 步  多主题
         第 2 套主题（暖纸质 warm-paper）+ 换肤验证 JSON 结构是否真的解耦

第 3 步  工程化
         抽 engine 为纯模块 → 补 Python/Node CLI → Git 仓库 + CHANGELOG

第 4 步  可选增强
         Agent Skill 层：LLM 负责润色与挑关键词，再由本引擎渲染

第 5 步  公开发布（视情况）
         静态产物丢 Pages/Vercel；主题市场？先看前面跑得顺不顺
```
