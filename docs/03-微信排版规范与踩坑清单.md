# 微信公众平台编辑器规范 · 实战摘录

> 来源：https://developers.weixin.qq.com/doc/service/guide/product/plugin_spec.html
> 《微信公众平台编辑器插件开发规范》。本文只摘录**排版时真正会踩到**的条款，并给出对应写法。
> 校验提示出现时，先用本表定位，再决定改不改——**多数提示不影响发布**。

---

## 0. 总原则

- 校验给出的**是提示，不是阻断**。文章照样能发。
- **第 0.1 条（最高优先级）：先确认内容是干净进剪贴板的。** 绝大多数「文字对齐异常」不是模板写错，而是**从渲染页 Ctrl+A/Ctrl+C 复制**时被浏览器塞进了计算样式（见上方 §0.5）。**先排这条，再排其他。**
- 微信的段落计数 ≠ 我们数 `<p>`。规范里「段落节点」= **顶层 `<section>` / `<p>`**；实测微信还会把图片块、空占位块也算进去，所以**不要靠自己的计数定位**，用编辑器里的「定位」按钮。
- **凡是规范没点名的属性，一律不要动。** 为消除提示而大面积重写布局，代价远大于提示本身（血泪教训：为消 2 条提示拆掉 flex，制造了十几条异常）。

## 0.5 🔴 头号污染源：复制链路（必读，优先级高于一切）

**现象**：模板完全合规、本地校验 0 错 0 警，粘进公众号编辑器后却报「文字对齐异常」。

**真因**：从**浏览器渲染页**里 `Ctrl+A/Ctrl+C`（或 `selectNodeContents` + `execCommand('copy')`）复制时，Chrome/Edge 会把**渲染后的计算样式**整个序列化进剪贴板。典型指纹 —— 这些属性人根本不会手写：

```
font-variant-ligatures  font-variant-caps  orphans  widows
-webkit-text-stroke-width  text-decoration-thickness
word-spacing  text-transform  text-indent  white-space
```

而这一坨里头藏着 **`text-align:start`** —— 正是规范 §1.6 明令禁止的取值，直接触发「文字对齐异常」。

**受控实验（Playwright + Chromium，同一台机器、同一份源文件、只读剪贴板）**：

| | A · 原始 html 用 Chrome 打开后「全选复制」 | B · 预览页点「复制到公众号」按钮 |
| -- | ---- | ---- |
| 剪贴板 text/html 体积 | **125,177** | **94,216**（小 25%） |
| 计算样式污染 | **570 处**（57 个节点） | **0** |
| `text-align:start` | **53** | **0** |
| **`display:flex`** | **0 ← 被抹掉了** | **14（完好）** |

结论两点，比预想的更严重：
1. 手动屏幕复制会引入 `text-align:start` → **「文字对齐异常」**；
2. 它还会**把 `display:flex` 整个抹掉** → 两栏卡片、签名行、END 线等所有 flex 布局塌掉。

也就是说手动复制不只是"多一堆垃圾属性"，而是**真的会改坏结构**。这解释了为什么历史上手动贴完会出现一堆错位。

**本质区别一句话**：手动 Ctrl+A/Ctrl+C = 交给浏览器「序列化屏幕上渲染出来的东西」；点按钮 = 把「原始 HTML 字符串」直接投递进剪贴板。前者经过浏览器这条脏水管，后者绕开它。**与模板无关，与微信无关。**

| | 已发布的专业文章（零告警） | 从渲染页复制的（两条告警） |
| -- | ---- | ---- |
| 上述计算样式指纹 | **0 处** | **513 处（57 个节点）** |
| `text-align:start` | **0** | **53** |
| `text-align` 取值 | `justify`127 / `center`7 | `start`53 / `justify`39 / `center`38 |

对方那篇**一个都没有** → 说明是**程序化写入剪贴板**，不是屏幕复制。

**正解**：把原始 HTML 字符串直接写进剪贴板，绕开浏览器的 DOM 序列化：

```js
await navigator.clipboard.write([new ClipboardItem({
  'text/html' : new Blob([RAW_HTML], {type:'text/html'}),
  'text/plain': new Blob([plainText],  {type:'text/plain'})
})]);
```

本 skill 的 `scripts/wrap_preview.py` + `assets/preview-template.html` 已改成这个方案。
**务必让用户用预览页的「复制到公众号」按钮复制，不要手动 Ctrl+A/Ctrl+C。**

**发布后立即体检**：`python scripts/check_published.py <文章URL 或 .mhtml>`
会直接报告指纹命中数、`text-align` 分布、渐变配额，退出码 1 表示不干净。

**注意中间状态没用**：实测把 `135deg` 压到与对照稿相同的 2 处，**提示依然存在**。所以只有两个有效选项：保留（接受 1 条提示）或全去（零提示）。

**关于对照稿为什么不告警（推论，未证实）**：对照稿发布于 2026.09，我方文章发布于 2026.10，两者渐变结构完全一致却结果不同 —— 推测微信在此期间收紧了深色模式检测。**这意味着"照抄旧文的渐变写法"这条路已经不安全了**，现在应当直接走无渐变变体。

## 1. CSS 属性使用规范（第 1 章）

| 条款 | 禁止/问题 | 影响 |
| -- | ---- | ---- |
| 1.1 opacity | `img` 设 `opacity:0` 再用 SVG 背景图叠加 | 发布后后台无法修改图片 |
| 1.2 caret-color | 设为全透明 | 编辑器光标不可见 |
| 1.3 line-height | 行高 < 字号且多行文字 | 行重叠。**例外**：内部无文字（图片拼接）；或渲染后仅单行 |
| 1.4 width | 固定宽度 | 居中不一致 / 溢出 / 各屏宽度差异。**豁免**：`data-ignore-width`（节点+子树全豁免） |
| 1.5 height | `height:0` 藏文字、内容溢出容器 | 移动端不可见。**例外**：SVG 内部、SVG 交互容器、无文字 |
| 1.6 text-align | 设为 **`start` / `end`** | 各终端解析不一致（部分居中、部分居左） |
| 1.7 begin | SVG `animate` 只写 `touchstart` | PC 端无法触发，须写 `touchstart; click` |
| 1.8 pre | 用 `<pre>` 包普通段落 | 窄屏不换行被截断。用 `<section>`/`<p>` |

**1.6 注意**：规范**只**点了 `start` / `end` 两个值。`left` / `center` / `right` / `justify` 都是标准值，`justify` 在大量已发布文章中普遍使用。若报「文字对齐异常」但全文没有 `start`/`end`，**不要猜**，用编辑器的「定位」按钮确认节点。

**图片宽度建议**：给 `<img>` 加 `data-w="原图像素宽"`，否则加载超时时检测引擎无可靠宽度、可能误报。

### 1.9 媒体占位：必须用「真实可渲染的图」，禁止假 URL（实测踩坑，比规范更致命）

给用户留「待替换」位时，**绝不能用** `src="__IMG_SRC__"`、`https://example.com/x.jpg`
或本地路径。微信编辑器只会显示「图片载入失败」+ 重试，**没有可点击的替换目标**；
用户强行替换还会破坏外层排版（实测：用户原话「我强行替换上去只会破坏掉原本的排版」）。

**正确做法**：生成一张**真实的占位图**（图上直接写明替换方法——用户看的就是这张图），
以 `base64` 内联进 `src`。

| 规则 | 说明 |
| -- | -- |
| 图上写替换说明 | 用户看到的就是这张图，文字要 actionable（「选中本图 → 上传覆盖即可」） |
| 带 `data-w` + `data-ratio` | 微信据此预留高度，避免图片加载完跳一下 |
| **`video` 一律落图片占位** | 公众号放不了 `<video>`，唯一路径是「后台素材库上传 → 插入 → 删掉占位图」。图注要带原视频文件名，提示该传哪一个 |
| 只对空 src / 伪地址回落 | 真实 URL 放行，否则误判用户自己的图 |
| 临时链接要单独警告 | 飞书 `authcode` / OSS 签名直链几小时就过期，粘进去当场能看、过会儿变死图 |

参考实现：`E:\fengdu\gzh-studio\check\make_placeholders.py`（生成封面 1080×460 /
正文图 1080×720 / 视频 1080×608 三张，编译成 `engine/placeholders.js`）。

## 4. Dark Mode（第 4 章）

### 4.1.2 文字背景尽量不要使用渐变
渐变背景若**上方有文字**，算法会先对渐变做 mix 混合、**转成纯色**再转换，以降低不确定性。

### 4.1.3 纯背景可以使用渐变 ✅
> **渐变背景上方若无文字，算法将不对该渐变进行处理（会被保留）。**

即：装饰用的渐变条、渐变色块（内部只放 `<span leaf=""><br></span>` 或 `&nbsp;`）**不会被处理，也不会报违规**。这是最干净的规避方式。

```html
<!-- 合规：渐变装饰线，内部无文字 -->
<span style="height:1px;background:linear-gradient(90deg,#bfdbfe,rgba(191,219,254,0));display:inline-block;font-size:0;line-height:0;"><span leaf="">&nbsp;</span></span>
```

### 4.2.1 多个文本共用一个背景 → 把背景写到容器上
不要把同一个渐变/背景色重复写在每个文本节点上，写在公共容器上（性能 + 避免问题）。

### 4.2.2 保持正确嵌套
严禁绝对定位/变形破坏视觉与结构顺序的一致（不要把文本定位到没有从属关系的背景节点上）。

### 4.5.1 `data-no-dark`
指定节点跳过算法转换，**仅当前节点生效**，后代若有内联样式仍会转换。

### 4.6 豁免机制 `data-ignore-dm` ⭐
> 创作者如果已充分了解警告，并确认 Dark Mode 效果没问题，可添加 `data-ignore-dm` 告知校验引擎**跳过该节点**的指定规则检测。

属性值填要忽略的规则，多个用空格分隔：
- `low-contrast` —— 跳过「文字与背景色对比度太低」
- `text-bg-gradient` —— 跳过「文字背景尽量不要使用渐变」

```html
<section data-ignore-dm="low-contrast text-bg-gradient">...</section>
```

**生效范围**：仅标记的节点本身；**后代节点若自身违规，仍会检测并提示**——所以每一处渐变节点都要各自加。

## 实战决策表：遇到提示怎么办

| 提示 | 首选方案 | 备选 |
| -- | ---- | ---- |
| `darkmode-no-gradient` | ① 确认是否「渐变上方压着文字」；② **把压文字的 `135deg` 卡片底转纯色，配额压回 2 处**；③ `90deg` 装饰线全保留 | 加 `data-ignore-dm="text-bg-gradient"`（绕过而非解决，**不推荐**——见下） |
| 「文字对齐异常」 | ① 全文搜 `text-align:\s*(start\|end)`；② 用「定位」按钮拿到具体节点；③ **确认该节点有没有多余的 `text-align:left`** —— 见下方专节 | 提高显式 `text-align` 覆盖率（只补 `justify`/`center`） |
| 宽度类 | 加 `data-ignore-width` | 改百分比宽度 |
| `height:0` 藏文字 | 去掉 height:0 | —— |

**反面案例（务必避免）**：为消除 `darkmode-no-gradient` 与「文字对齐异常」两条提示，把全文 `display:flex` 全部拆成 `inline-block` 重搭分栏。结果：宽度需手算、`font-size:0` 除间隙、`vertical-align`、`white-space` 副作用连环爆，方案对照/签名卡/END 线/看点卡全部错位，**2 条提示变成十几条异常**。

**佐证**：已发布的同风格文章（`mp.weixin.qq.com/s/TPzww8h6m_oOn_V5jhmdIA`）实测含 `linear-gradient` 5 处、`display:flex` 9 处且 9 个全未声明 `text-align`、`text-align` 仅用 `justify`(127)/`center`(7)——**微信容忍 flex，也容忍这类渐变**，原文本身就是这么发的。

## 「文字对齐异常」专节：`left` 才是雷

**结论**：做"把隐式 `text-align` 写成显式"这种恒等变换时，**继承值是 `left` 的节点必须保持裸奔**。

**证据链**（对照组 = 已发布、零告警的 mhtml）：

| 取值 | 已发布（零报错） | 初版 | 全量补 align 后 |
| -- | ---- | ---- | ---- |
| `justify` | 127 | 39 | 81 |
| `center` | 7 | 13 | 38 |
| **`left`** | **0** | **0** | **50** |

补 align 后微信点名的 END 分隔线 span，与已发布版的**唯一差异**就是多了一个 `text-align:left`。删掉全部 50 个 `left` 后，该 span 与已发布版**逐字节一致**。

**为什么删掉是安全的**：`left` 就是 CSS 默认值，显式写与不写渲染结果完全相同 —— 纯恒等回退，零视觉风险。

**落地规则**：
- 补 align 脚本的准入条件改为：`inherited in ('justify','center')` 才补；`left` 直接跳过。
- 已有文件自检：`grep -c 'text-align:left'` 应为 **0**。
- 改完把 END 段跟已发布版逐字节比对一次。

**方法论沉淀**：这类排查不要猜，**一定要有"已发布且零告警"的对照组**，用 diff 找唯一差异。靠推理定位过一次 END 分割线，结果被对照组证伪了一次。

**⚠️ 更重要的教训：告警消失 ≠ 问题解决。** 删掉 `text-align:left` 后 `darkmode-no-gradient` 从"第 108 段"挪到"第 1 段"，当时误判为"修好了" —— 实际上那只是改变了检测顺序。**判断"有没有解决"的唯一标准是用户可见的效果**，不是编辑器里的提示数量。这次是用户拿手机一看，才发现渐变容器里的字根本看不见。

→ **凡涉及到视觉/渲染类告警，修完必须让用户用真机（且开深色模式）验一遍，不能只看编辑器提示消失。**

## `darkmode-no-gradient` 专节：按 §4.1.3 精准切分

**§4.1.2 说了什么**：文字背景尽量不要用渐变 —— 深色模式下算法会把渐变 mix 成纯色，**文字颜色不跟着翻转**，于是深色字压深色底，**肉眼不可见**。

**用户实测到的就是这个**：手机上看不到渐变容器里的字，**光标选中反色后才看得出来**。这是硬性可用性缺陷，不是"提示而已"。

**§4.1.3 的解法很直接**：渐变**上方无文字**时算法不处理。所以：

| 类型 | 例子 | 处理 |
| -- | -- | -- |
| `90deg` 装饰渐隐线 | END 左右线、刊头顶部横线（内部只有 `<span leaf=""><br></span>` 或 `&nbsp;`） | **全部保留**，天然合规 |
| `135deg` 卡片底（**有文字**） | 卡片头部、行动引导卡、对照卡头部 | **按配额保留 2 处，其余转起始纯色** |

**配额怎么定**：直接数对照组。已发布零告警原文 5 处渐变 = 3 条 `90deg` 装饰线 + **2 处 `135deg` 卡片底**（刊头卡 + 签名卡）。这两处之所以安全，是因为渐变的**终点是纯白** `#ffffff`，mix 后接近白底，深色字仍可读 —— **是"刚好够用"，不是可以随意加的额度**。

**落地脚本要点**：按**容器特征**做白名单精确保留（如 `padding:15px 17px 17px` / `margin:0 4px 24px`），其余按类型转纯色；生成后跑一遍「(角度, 所在容器) 二元组」与对照组比对，两者应**完全一致**。注意比对前要把 `padding: 15px` 这种冒号后的空格归一化，否则会误报不一致。
