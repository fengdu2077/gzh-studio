# 04 · 主题开发规范（草案）

> 目标：**新增一套主题 = 新增一个 JSON 文件，引擎代码一行不改。**
> 本文是草案，第一套主题落地后应回头校准。

---

## 1. 主题文件三层结构

```jsonc
{
  "id": "blue-editorial",
  "name": "科技刊读风",
  "version": "1.0.0",

  // ① 设计变量：决定"颜色/字号/间距"，换肤层
  "tokens": {
    "accent":     "#2563eb",
    "accentSoft": "#eff6ff",
    "border":     "#dbeafe",
    "textMain":   "#374151",
    "textStrong": "#111827",
    "textMuted":  "#9ca3af",
    "shadow":     "0 3px 12px rgba({{accentRgb}},0.06)"  // 引用，别写死，见 §3.2
  },

  // ② 基础排版：决定正文观感
  "base": {
    "fontSize": "15px",
    "lineHeight": 1.95,
    "letterSpacing": "0",
    "align": "justify",
    "fontFamily": "'PingFang SC','Hiragino Sans GB','Microsoft YaHei',sans-serif",
    "chapterGap": "60px",
    "paraGap": "20px"
  },

  // ③ 组件模板：决定结构，每个模板是一段合规的微信 HTML
  "components": { /* 见第 3 节 */ },

  // ④ 防呆规则：把本轮踩的坑固化成机器可校验的阈值
  "rules": {
    "maxGradient135": 0,      // 压文字的卡片底渐变上限（0 = 走无渐变变体）
    "maxGradientTotal": 3,    // 仅允许 90deg 无文字装饰线
    "forbidTextAlign": ["left", "start", "end"],
    "requireImgDataAttrs": ["data-w", "data-ratio"],
    "requireLeafSpan": true,
    "allowFlex": true
  }
}
```

**为什么分三层**：`tokens` 换色、`components` 换结构、`rules` 换约束。
只改 `tokens` 就能出一个同结构新配色的皮肤；只改 `components` 就能出一个全新版式。**两者都不动引擎。**

## 2. 组件清单（role 表 = 28 个，主题挑着实现）

> **组件 key 必须等于 role 名，role 表以 `docs/07` 为准（本文不再重复列全表）。**
>
> ⚠️ 更正：本文早先写过「实际实现的 role 是 13 个，早期 18 个是照抄竞品」——**这句话已作废**。
> 13 是 `blue-editorial` 这一套主题的**实现覆盖率**，不是 role 总数。
> 把「这套主题用到了几个」当成「系统支持几个」，是拿实现倒推契约，会直接砍掉工具的表达能力。
>
> **区分两件事**：
> - **role（28 个，稳定）** = 语义槽位，引擎契约。`docs/07` §2 是唯一权威来源。
> - **component（每套主题不同）** = `theme.components[role]`，主题作者**挑其中一部分实现即可**。

主题缺失某个 role 时的行为（**任何情况下都不会报错、不会留白**）：

1. 先找近亲组件（如 `tip` → `note`、`compare` → 两张独立卡片）
2. 再找引擎内置 `FALLBACK`
3. 详见 `docs/06` §5.2 降级链

**新主题的最低要求**：实现 L0 骨架层 8 个（`masthead`/`chapter`/`para`/`list`/`quote`/`image`/`divider`/`signature`）。
其余 20 个按需挑选，**挑得越少越省事，只是精细度低一点**。

`blue-editorial` 当前实现 **14 / 28**（覆盖 L0 全部 + `note`/`compare`/`cta`/`highlights`/`video`/`profile`）。

> **`profile` 作者卡**需要注意：`:::profile` 与旧的 `signature`（front-matter author 自动追加）
> **是两套独立入口**，主题里通常都要实现。`profile` 登场后它就取代了 `signature` 的主力位置
> —— 差别只在来源：`profile` 是用户手写的盒子，`signature` 是兼容旧稿的自动追加。
> 字段：`author` / `initial`（头像首字，引擎派生）/ `roleline` / `bio` / `footer` / `account`。

> **`image` 与 `video` 的特殊约定**：`src` 可能是一张 **base64 占位图**（见 `docs/06` §4.1）。
> 写这两个组件的模板时，**必须带上 `{{?w}} data-w="{{w}}"{{/w}}{{?ratio}} data-ratio="{{ratio}}"{{/ratio}}`**，
> 让微信据此预留高度，否则图片加载完会跳一下。
> 另外 `video` 的模板与 `image` 同构即可——公众号里视频也是「一张图 + 说明」，
> 真正的视频靠用户去素材库上传后替换。

**两条容易忽略的反推约定**（`blue-editorial` 实测）：

- **间距挂外层 `<section>`，`<p>` 一律 `margin:0`**。57 个模块无一例外。
  微信对 `<p>` 的默认 margin 处理不可靠，靠 `<p>` 撑间距会出问题。
- **`compare`、`signature`、`endline` 用 `display:flex`**。flex 在微信里可用（已发布文章实测），
  但**降级时绝不能拆 flex**——历史惨案：把 flex 拆成 `inline-block` 导致十几处排版崩。

## 3. 组件模板写法

每个组件是一段**完全符合微信约束**的 HTML 字符串，用 `{{slot}}` 占位：

```jsonc
"para": {
  "from": "paragraph",
  "wrap": "<section style=\"margin-top:{{paraGap}};\"></section>",
  "tpl":  "<p style=\"margin:0;font-size:{{fontSize}};line-height:{{lineHeight}};text-align:{{align}};color:{{textMain}};letter-spacing:{{letterSpacing}};\"><span leaf=\"\">{{content}}</span></p>"
}
```

**硬性要求（否则会被微信吃掉）**：
- 布局只用 `<section>`，**不允许 `<div>`**
- 禁止 `class` / `id` / `<style>` / `<script>`
- 所有样式必须 `style` 内联
- 每个文本叶子必须 `<span leaf="">` 包裹
- 属性顺序建议固定，方便日后做 diff

### 3.1 条件段必须成对，括号一个都不能少 ⚠️

模板里两种占位（`engine/core.js:38` 的正则）：

```
{{key}}               普通变量，缺失填空串
{{?key}} … {{/key}}   条件段，值为空时整段不输出
```

**写残了就静默输出字面量。** `fill()` 只认合法语法，匹配不上就原样吐出去 ——
不报错、不警告，用户直接看到满屏 `{{?account}}` 出现在文章正文里。

>`docs/07` 的作者卡就真的踩过：模板被写成 `{{?account} … {/account}`（**两个端点各少一个括号**），
>产物里多出 53 个字符的残缺标记，是拿渲染字节数逐字节比对才发现的。
>症状图见 commit 记录，用户原话：「作者卡渲染出来的东西显示不对」。

**两道机器闸门**（别再靠肉眼）：

| 位置 | 检查什么 | 失败后果 |
| -- | -- | -- |
| `check/build_theme_js.py` | 残缺括号 + 开闭不配对 | **拒绝编译**，`.js` 不产出，附具体行内位置 |
| App 体检第 7 片 `模板` | 产物里是否有 `{{?` / `{/x` / `{{x}}` | **禁用复制按钮**并给出拦截理由 |

所以改完主题的正确顺序是：改 `themes/*.json` → 跑 `build_theme_js.py`（闸门在这一步拦）→
`node check/test_engine.js`（看 `模板残留` 是否为 0）→ 浏览器预览。

### 3.2 引用与派生：色值绝对不能抄第二遍

模板做到「零硬编码色值」还不够 —— **色值还会藏在 token 的值里**。
`shadow` 曾经写成 `rgba(37,99,235,0.06)`（蓝的 RGB 直接写死），
模板区明明是干净的，换主色之后卡片变绿了、外圈那抹阴影还是蓝的。
渐变端点还有过 `rgba(37,99,235,0)`：alpha 是 0 所以肉眼根本看不见，只有字符串比对能发现。

两条机制专门治这个，都由 `engine/core.js` 的 `prepareTheme()` 提供：

**① 引用**：token 的值里可以写 `{{另一个token}}`，渲染时展开。

```jsonc
"shadow":         "0 3px 12px rgba({{accentRgb}},0.06)",
"shadowMasthead": "0 4px 14px rgba({{accentRgb}},0.06)"
```

**② 派生**：每个 `#rrggbb` 形式的 token 会自动多出一个同名的 `Rgb` 三元组。

```
accent       #2563eb   →   accentRgb       37,99,235
accentTint2  #bfdbfe   →   accentTint2Rgb  191,219,254
```

`rgba()` 要的是三元组而不是 hex，没有它，模板里就只能写死三元组。
**自动派生而不是让主题逐个手写**，是为了避免「加一个颜色 token 还得记得加一个 Rgb」。

**③ 行内标记的配色**（`**加粗**` / `` `代码` `` / `[链接]`）以前写死在
`engine/core.js` 的 `inline()` 里，主题完全管不到。现在默认引用同名 token：

| 部位 | 默认引用 | 兜底值（主题没给 token 时） |
| -- | -- | -- |
| 代码底色 | `{{accentSoft}}` | `#eff6ff` |
| 代码字色 | `{{accent}}` | `#2563eb` |
| 链接色 | `{{accent}}` | `#2563eb` |
| 链接下划线 | `{{accentTint2}}` | `#bfdbfe` |
| 加粗色 | `{{textStrong}}` | `#111827` |

想单独定制（比如链接不想跟主色一样）就在主题里写 `inlineStyle` 覆盖，不用改引擎。

**守卫**：`node check/test_recolor.js` 会把主色整套换成绿色再渲染，
逐个 token 查旧值残留，残留 > 0 就退出码 1。**加新组件后记得跑它。**

## 4. 新增主题的标准流程

1. 复制 `themes/_template.json`（待建）→ `themes/<新id>.json`
   **不用改 `app/index.html`** —— 主题是按 `GZH_THEME_ORDER` 动态加载的，
   编译完刷新页面下拉里就出现（以前每加一套都得去 HTML 里手写一行 `<script>`）
2. 改 `tokens`（先定色板）
3. 改 `base`（字号 / 行高 / 对齐）
4. 逐个填 `components`，每填一个就在 Web App 里预览
5. 填 `rules`，**尤其是 `maxGradient135`**
6. 用 `samples/demo.md` 全流程跑一遍
7. 跑 `node check/test_recolor.js` —— 换主色不能有旧色残留（重点看 shadow 和渐变端点）
8. 贴进公众号草稿 → 跑 `check/check_published.py` → 污染必须为 0
9. **拿手机开深色模式验一遍**（这条历史上救过命）

## 5. 变体（Variant）

同一个主题可以有派生变体，例如 `blue-editorial` 的「渐变版 / 无渐变版」。
实现建议：**不复制整份 JSON**，而是在主题文件里放 `variants` 字段做局部覆盖：

```jsonc
"variants": {
  "no-gradient": {
    "name": "科技刊读风（无渐变）",
    "overrides": { "rules.maxGradient135": 0 }
  }
}
```

这样改一次衍生规则，两个变体同步生效，不会出现两边漂移。
