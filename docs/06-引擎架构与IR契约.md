# 06 · 引擎架构与 IR 契约（草案）

> **本文是 `engine/` 的实现说明书，也是整个项目的地基。**
> IR 是三条入口（Web App / 大模型 / CLI）的**唯一交汇点**。不定死它就动手写代码，三条链路一定会各写各的。
>
> 反推依据：`samples/输出样例-blue-editorial-无渐变.html`（已实测零告警的 v5 成品），抽出的57 个顶层模块见 §2.4。**本文所有 role 与数值都来自真实成品，不是设计出来的。**

---

## 0. 一句话

```
把「这是什么」和「长什么样」彻底劈开：前半允许 AI 参与，后半必须是确定性代码。
```

IR 只回答「这是什么」（role + 内容），**不含任何 HTML、颜色、字号**。由此带来两个能力：

1. **同一份 IR 喂给任意主题都能出成品** → 多主题成立的前提
2. **渲染结果 100% 确定** → 同一输入永远同一输出，可回归测试

---

## 1. 六阶段管线

| # | 阶段 | 输入 | 输出 | 谁负责 | 是否碰外观 |
| -- | -- | -- | -- | -- | -- |
| ① | 输入 | 用户粘贴 / 文件读取 | Markdown 字符串 | `app.js` | 否 |
| ② | 解析 | Markdown | AST / token 流 | `parse.js`（包 `marked`） | 否 |
| ③ | **语义提升** | AST | **IR**（纯结构） | `ir.js` | **否 ← 分界线** |
| ④ | 渲染 | IR + 主题 JSON | HTML 片段 | `render.js` | 是 |
| ⑤ | 后处理与校验 | HTML + `rules` | 合规 HTML + 体检报告 | `sanitize.js` | 是 |
| ⑥ | 投递 | 合规 HTML | 剪贴板 | `clipboard.js` | 否 |

**分界线划在 ③ 和 ④ 之间。** ③ 之前禁止出现任何颜色/字号/布局信息，④ 之后禁止根据内容做语义判断。

### 核心渲染循环（全文最重要的一段伪代码）

```js
function render(md, theme, variant) {
  const ir    = toIR(parse(md));            // ②③ 纯结构，零外观信息
  const irv   = applyVariant(ir, variant);  // 变体：局部覆盖，不复制整份主题
  const html  = irv.blocks.map(block => {
    const comp = theme.components[block.role]   // 主题没写这个组件
              ?? FALLBACK[block.role];          // → 降级，绝不报错
    return fill(comp, { ...theme.tokens, ...theme.base, ...block });
  }).join('');
  return sanitize(html, theme.rules);        // ⑤ 补叶节点 / 内联化 / 阈值卡口
}
```

**`theme.components[block.role] ?? FALLBACK[block.role]` 这一行，就是「新增主题不用写全组件」的全部实现。**
详见 §5 的降级链。

## 2. IR 数据结构

### 2.1 顶层：Document

```ts
type Document = {
  meta: Meta,          // 来自 front-matter，见 §3.1
  blocks: Block[],     // 有序。渲染时按顺序拼，不做重排
}

type Meta = {
  title:      string,   // 文章标题
  cover?:     ImageRef, // 封面图
  author?:    string,   // 作者名（默认取全局配置）
  account?:   string,   // 公众号名
  issue?:     string,   // 刊期，如 "2026.10"
  kicker?:    string,   // 眉标，如 "EDITOR'S NOTE"
  lede?:      string,   // 导语（刊头卡里的那句提炼）
  highlights?:string[], // 看点清单，会渲染成编号卡
  lang?:      'zh' | 'en',
}
```

### 2.2 中层：Block（role 共 28 个，见 `docs/07`）

> ⚠️ **role 表以 `docs/07` 为准，本文不重复列全表。**
>
> 更正：本文早先写「13 个 role 是从成品反推的」——**这句已作废**。
> 13 是 `blue-editorial` 这套主题的实现覆盖率；**从单一成品反推只能得到「这个成品用了什么」，
> 推不出「这套工具应该支持什么」**。拿它当 role 总数会让后来人以为系统只有 13 种表达能力。
>
> role 是**语义契约**（稳定、与主题无关），分三层：
> - **L0 骨架层 8 个**：`masthead` `chapter` `para` `list` `quote` `image` `divider` `signature`
> - **L1 常用层 11 个**：`note` `tip` `warning` `compare` `steps` `cta` `highlights` `toc` `code` `table` `endline`
> - **L2 场景层 9 个**：`gallery` `stats` `timeline` `faq` `callout` `keyvalue` `video` `audio` `footer`
>
> 另有正交维度 `tone`（`info`/`tip`/`warn`/`danger`/`success`/`verdict`），**不占 role 名额**。

```ts
// 完整枚举见 docs/07 §2。主题只需实现其中一部分，缺失走 FALLBACK。
type Role =
  // L0 骨架
  | 'masthead' | 'chapter' | 'para' | 'list'
  | 'quote'    | 'image'   | 'divider' | 'signature'
  // L1 常用
  | 'note' | 'tip' | 'warning' | 'compare' | 'steps'
  | 'cta'  | 'highlights' | 'toc' | 'code' | 'table' | 'endline'
  // L2 场景
  | 'gallery' | 'stats' | 'timeline' | 'faq'
  | 'callout' | 'keyvalue' | 'video' | 'audio' | 'footer'
  ;

type Tone = 'info' | 'tip' | 'warn' | 'danger' | 'success' | 'verdict';

type Block = {
  role:  Role,
  tone?: Tone,          // 情绪标记，不占 role 名额（docs/07 §3）
  id?:   string,        // 稳定标识，便于日后做增量 diff
  level?:number,        // chapter 专用：heading 级别
  index?:number,        // chapter 专用：自动编号，从 1 开始
  title?:string,
  subtitle?:string,     // chapter 的英文副标题，如 "THE CHALLENGE"
  label?:string,        // 卡片眉标，如 "校核结论 · VERDICT"
  text?: string,        // 正文文本（含内联标记）
  cite?: string,        // 出处（quote / callout 用）
  items?:Item[],        // list / highlights / toc / faq / stats / timeline 通用；
                        //   纯字符串数组时按 list 语义处理
  src?:  string,        // image / video / audio 用；可能是 base64 占位图
  w?:    number,        // 图片原始宽度（微信据此预留高度）
  ratio?:number,        // 高/宽
  placeholder?:boolean, // true = 这是占位图，发布前应替换（见 §4.1）
  caption?:string,      // 图注
  columns?:CompareCol[],// compare 用
  images?:ImageRef[],   // gallery 用
  cols?:  number,       // gallery 用：并排列数 2 / 3
  head?: string[],      // table 用：表头
  rows?: KV[] | string[][], // table（二维数组）/ keyvalue（KV 数组）用
  ordered?:boolean,     // list / steps 用
  href?: string,        // cta 用
  meta?: Record<string, unknown>,  // 组件私有字段
}

type CompareCol = { title: string, badge?: string, items: string[] }
type ImageRef   = { src: string, w?: number, ratio?: number, alt?: string }
type Item       = string | { q?:string, a?:string,                 // faq
                             no?:string, title?:string,            // toc
                             value?:string, label?:string, unit?:string, // stats
                             time?:string, title?:string, text?:string } // timeline
type KV         = { k: string, v: string }
```

### 2.3 内联标记

**不做完整的行内 AST**，只保留微信能表达的三种，够用了：

| Markdown | IR 表达 | 渲染为 |
| -- | -- | -- |
| `**加粗**` | `«strong»…«/strong»` | `#111827` + `font-weight:600` 的 `<span>` |
| `` `代码` `` | `«code»…«/code»` | 等宽 + 浅底的 `<span>` |
| `[文字](链接)` | `«link href="…"»…«/link»` | 微信可点链接（正文外链受限，谨慎） |

> 用 `«»` 而不是 `<>` 做标记，是为了避免和 HTML 混淆、也省掉一层转义地狱。
> **推测**：这套够覆盖公众号场景；若将来要支持上下标/高亮，再扩展，不要在 MVP 里做。

## 3. 输入契约：Markdown 扩展语法

### 3.1 为什么必须有扩展：原生 Markdown 表达不了

从 `samples/demo.md` 实测：

| 成品里有的 | Markdown 原生语法 | 能对应吗 |
| -- | -- | -- |
| 刊头卡（眉标 / 导语 / 封面） | 无 | ❌ |
| 看点清单 HIGHLIGHTS | 无 | ❌ |
| 两栏对照 COMPARE | 表格勉强 | ⚠️ 表格在微信里表现很差 |
| 行动引导 CTA | 无 | ❌ |
| 章节英文副标题 | 无 | ❌ |
| END 分隔线 / 签名区 | `---` | ✅ 已按位置分流：文中 → `divider`，文末最后一条 → `endline`（见 `ir.js` 的 `toIR()` 末尾） |

**`demo.md` 里一行 front-matter 都没有**，所以这几类内容目前只能靠人手工补。
这是第一版必须先解决的事——否则工具只能「半自动」。

### 3.2 front-matter（顶层元数据）· **兼容路径**

> ⚠️ **front-matter 已不再是推荐写法。**
> 它的问题是：整篇只能有一份，于是所有字段被迫绑在一起，位置也由解析器决定。
> 用户反馈的真实症状是「先插刊头卡、后插作者信息，作者信息会被塞到刊头卡旁边」。
> 现在的推荐写法是**每个盒子自包含**（`:::masthead` / `:::profile`，见 §3.3）。
> front-matter 依旧能工作，走的是同一批盒子，**但只在用户没手写同名盒子时生效**（手写优先，见 §4.2）。

文件开头用 `---` 包一段 YAML：

```markdown
---
title: 豆包能看懂户型图了，我试出了一个能走进去的 3D 样板间
cover: ./cover.jpg        # 1080×460，约 2.35:1
author: 风渡
account: 风渡2077
issue: 2026.10
kicker: EDITOR'S NOTE
lede: 以前大模型看图只能看懂画了什么，现在开始能看懂尺寸和空间关系了。
highlights:
  - 一张户型图能直接变成可互动的 3D 毛坯房
  - 三张照片就能读出床的真实尺寸
---
```

| 字段 | 必填 | 缺省行为 |
| -- | -- | -- |
| `title` | ✅ | 取首个 `#` 标题，**结果转 `masthead`** |
| `cover` | ❌ | **自动落封面占位图**（1080×460），用户粘到公众号后替换。见 §4.1 |
| `author` / `account` | ❌ | 取 App 全局默认（你的就是「风渡 / 风渡2077」） |
| `highlights` | ❌ | 缺则整个 `highlights` 块不输出，**不留空卡** |

> **关于封面图的硬规定**（本轮踩过）：要给用户留「待替换」位时，**绝不能用假 URL 或本地路径**。
> 微信会显示「图片载入失败」，点了替换也换不掉，强行替会破坏结构。
> **正确做法**：生成真实的占位图并以 base64 内联。
> 具体实现见 §4.1 与 `check/make_placeholders.py`。
>
> ⚠️ front-matter 里**不要写行内注释**（`cover:  # 说明`）——极简 YAML 解析器会把
> `# 说明` 当成字段值。注释请写在正文里。

### 3.3 容器块 `:::xxx`

借鉴 md2wechat 的 `:::module` 语法，但**我们在本地解析**（这是必须本地渲染的又一个理由）。

````markdown
/* ① 刊头卡 —— 一个盒子装全部：key:value 行 + 首个 ## 标题 + 剩余正文当导语 */
:::masthead
## 这里写文章标题
cover: 
kicker: 本期实测
issue: 2026.10
account: 风渡2077
tagline: AI 实测

一句话导语，提炼全文最重要的那个结论。
:::

/* ② 作者卡 —— 同样是自包含盒子。放开头是作者简介，放文末是署名区 */
:::profile
account: 风渡2077
author: 风渡
roleline: CREATOR · AI PRACTITIONER
bio: 一两句话说清你是谁、在写什么。
footer: 如果觉得有收获，欢迎点赞、在看、转发三连。
:::

:::note 校核结论 · VERDICT
可以容纳，且空间宽裕。床占地约 4.6㎡，核心睡眠净区约 20.7㎡。
:::

:::compare
## 床头靠南墙 | 推荐
- 床头贴整面实墙，床尾正对电视柜
- 三边动线都在 1 米以上
## 床头靠北墙 | 不推荐
- 床体会逼进入户开口
:::

:::cta 如果你手上也有一张户型图，不妨照着这个顺序试一遍
先让 AI 把房子盖出来，再让它读尺寸、出平面图。
[在豆包里新建任务试试](https://...)
:::
````

| 容器 | 产出 role | 备注 |
| -- | -- | -- |
| `:::masthead` | `masthead` | **刊头卡**。盒内 `key: value` 行（cover/kicker/issue/account/tagline）+ 首个 `##` 当标题 + 剩余正文当导语 |
| `:::profile` | `profile` | **作者卡**。盒内 `key: value` 行；`initial`（头像首字）由 `author` 派生，不用手填 |
| `:::highlights <标题>` | `highlights` | **看点卡已独立成块**，不再只能塞在 front-matter 里；内部列表项即看点 |
| `:::note <标题>` | `note` | 首行即卡片标题（`·` 后是英文副标题） |
| `:::compare` | `compare` | 内部每个 `##` 是一栏，`\|` 前标题后徽标 |
| `:::cta <引导语>` | `cta` | 最后一个链接自动渲染成按钮样式 |
| `:::quote` | `quote` | 等价于 `>` 块，用于需要标题的场景 |

### 3.4 位置约定

| 约定 | 说明 |
| -- | -- |
| 首个 `#` 是文章主标题 | 若有 front-matter `title`，以 front-matter 为准 |
| 所有 `##` 按出现顺序编号 | 自动补零成 `01`…`07`，**不写死数字** |
| `##` 标题里 `@` 后是英文副标题 | 如 `## 写在最后 @REFLECTION` → `subtitle` |
| 文件末尾的 `---` | 渲染成 `endline`（END 线），而非普通分割线 |
| `signature` 块始终输出在最后 | 内容来自 `meta.author` + App 默认文案，**不需要写在 md 里** |

## 4. Markdown → IR 映射表（核心）

`ir.js` 的唯一职责就是实现这张表。**有歧义时以本文为准。**

| Markdown 语法 | role | IR 字段 | 备注 |
| -- | -- | -- | -- |
| `:::masthead` | `masthead` | `title`,`lede`,`cover`,`kicker`,`issue`,`account`,`tagline` | **推荐写法**：自包含盒子，位置随意 |
| `:::profile` | `profile` | `author`,`initial`,`roleline`,`bio`,`footer`,`account` | 放开头=简介，放文末=署名区 |
| front-matter `title` | `masthead` | `meta.*` | **旧写法，保留兼容**：未手写 `:::masthead` 时才生效 |
| front-matter `highlights` | `highlights` | `items[]` | 自动编号 01/02/03（**旧写法，保留兼容**） |
| front-matter `author` | `signature` | `author`,`initial`,`bio`,`roleline` | **旧写法**：未手写 `:::profile` 时才追加 |
| `:::highlights <标题>` | `highlights` | `items[]` | **推荐写法**：独立成块，可自己决定放哪 |
| `# / ##` | `chapter` | `title`,`subtitle`,`index` | index 自动累加 |
| 普通段落 | `para` | `text` | 含内联标记 |
| `> 引用` | `quote` | `text` | 原文照抄类 |
| `:::note` | `note` | `title`,`text` | 作者判断类 |
| `:::compare` | `compare` | `columns[]` | 两栏 |
| `:::cta` | `cta` | `text`,`meta.action` | 末位链接成按钮 |
| `![alt](src)` | `image` | `src`,`caption` | 紧随其后的斜体段落当图注；**`src` 允许为空** |
| `xxx.mp4` 独占一行 | `video` | `src`,`caption` | **一律**转图片占位卡（见 §4.1） |
| `- 项` / `1. 项` | `list` | `items[]`,`ordered` | |
| ``` 代码块 | `code` | `text`,`lang` | 微信无 `<pre>`，见踩坑 §1.8 |
| 表格 | `table` | `rows[][]` | 建议降级处理 |
| 文末最后一条 `---` | `endline` | —— | 全文唯一；**文中的** `---` 是 `divider` |
| 文中的 `---` | `divider` | `style` | 节奏断点 |
| `:::tip` / `:::warning` | `tip` / `warning` | `title`,`text` | 共享 `note` 骨架，靠 `tone` 区分 |
| `:::steps` | `steps` | `items[{title,text}]` | |
| `:::toc` 或 front-matter `toc: true` | `toc` | `items[{no,title}]` | 自动收集 `##` |
| `:::gallery` | `gallery` | `images[]`,`cols` | |
| `:::stats` | `stats` | `items[{value,label,unit}]` | |
| `:::timeline` | `timeline` | `items[{time,title,text}]` | |
| `:::faq` | `faq` | `items[{q,a}]` | |
| `:::callout` | `callout` | `text`,`cite` | 金句大字 |
| `:::spec` | `keyvalue` | `rows[{k,v}]` | 参数/规格，比表格更适合手机 |
| `xxx.mp3` 独占一行 | `audio` | `src`,`caption` | 一律转占位卡 |
| `:::footer` / front-matter `footer` | `footer` | `text` | 版权/转载声明 |
| （约定）文末 | `signature` | `meta.author` | 自动追加 |

> **完整语法示例见 `docs/07` §4。** 未知容器 `:::xxx` 一律降级为 `para`，**不静默丢弃**。

### 4.1 媒体占位回落（`pickSrc`）

这是 IR 层唯一会「补内容」的地方，规则必须写死，否则主题再好也白搭。

**为什么需要**：公众号编辑器对加载失败的图片只显示「图片载入失败」+ 重试，
没有可点击的替换目标；用户强行替换还会破坏外层排版。所以**宁可先给一张真的能显示的
占位图，图上写明替换方法**。假地址（`https://example.com/x.jpg`）是最坏的做法——
它看起来像配好了，实际是个死链接。

| 输入 | 输出 | 说明 |
| -- | -- | -- |
| `cover` 空 / 伪地址 | `placeholders.cover.uri` | **刊头卡恒有封面**，缺图等于没做完 |
| `image` 的 `src` 空 / 伪地址 | `placeholders.image.uri` | 用户自己的真实 URL 一律放行 |
| `video` 任意 `src` | `placeholders.video.uri` | 公众号放不了 `<video>`，**没有例外** |

回落到占位图时会同时写入 `w` 与 `ratio`（微信据此预留高度，避免加载时跳动），
并在 IR 上打 `placeholder: true` 标记，方便将来做「发布前提醒未替换」的检查。

**判断「伪地址」的边界**：只认空串、`#`、`placeholder`、以及 `example.com|org` 域名。
**不做**「远程可达性探测」——纯静态无服务端，也避免误判用户自己的图。
飞书/图床的临时链接属于「真实 URL」，我们放行（失效是它自己的问题）。

**`video` 为什么必须无条件回落**：Markdown 里写的 `rec-convert.mp4` 对公众号毫无意义，
用户唯一的路是「后台素材库上传视频 → 插入到此处 → 删掉占位图」。
所以占位图上的文案要直接写这一步，图注带上原文件名（提示该传哪一个）。

> **`video` 占位为什么必须显式存在**：成品里 3 个 mp4 至今仍是空占位块。
> 让引擎把它渲染成一张「待补：xxx.mp4」的虚线卡，比静默丢弃好——
> 你可以一眼看见哪几处还没补素材。**这条是成品直接反推的，不是理论。**

### 4.2 容器里的 `key: value` 行与优先级

盒子里写 `cover: xxx` 这类行，靠的是 `grammar.kv`（见 §7.1）——**不用去文件头找对应字段**。

IR 生成走固定六步流水线：`static → kv → map → slots → derive → defaults`。
其中 `slots` 声明哪些字段要过 `pickSrc` 占位回落，`derive` 派生字段（如头像首字）。

**手写盒子优先于 front-matter**：`ir.js` 会先扫一遍 AST，记下用户写了哪些容器；
只有没手写同名盒子时，才把 front-matter 翻译成对应块。这样一篇文章不会长出两个刊头卡。

## 5. role → 组件映射与降级链（核心）

### 5.1 三档优先级（对应 `docs/07` §2 的 L0/L1/L2）

| 档位 | role | 主题缺失时的处理 |
| -- | -- | -- |
| **L0 骨架（8）** | `masthead`, `chapter`, `para`, `list`, `quote`, `image`, `divider`, `signature` | 引擎内置 `FALLBACK`，**必须能出成品** |
| **L1 常用（11）** | `note`, `tip`, `warning`, `compare`, `steps`, `cta`, `highlights`, `toc`, `code`, `table`, `endline` | 降级为近亲组件 |
| **L2 场景（9）** | `gallery`, `stats`, `timeline`, `faq`, `callout`, `keyvalue`, `video`, `audio`, `footer` | 降级为朴素渲染 |

### 5.2 降级链（二级）

查找顺序：`components["<role>.<tone>"] ?? components["<role>"] ?? <一级降级> ?? FALLBACK["<role>"]`。

第一级找**近亲组件**，第二级找**引擎内置朴素模板**。这样主题作者少写一半组件，效果也不会崩：

| role | 一级降级 | 二级降级（`FALLBACK` 内置） |
| -- | -- | -- |
| `masthead` | `chapter` | 大字 `<p>` + 作者行 |
| `highlights` | `list`（有序） | `<ol>` 朴素列表 |
| `note` | `quote` | 左侧细线的朴素块 |
| `tip` | `note`（tone=tip） | 左侧细线的朴素块 |
| `warning` | `note`（tone=warn） | 左侧细线的朴素块 |
| `quote` | `note` | 左缩进 + 灰色竖线 |
| `compare` | `table` | **两栏各渲染成一张独立卡片**（不拆 flex，避免重蹈覆辙） |
| `steps` | `list`（有序） | 有序列表 |
| `cta` | `note` | 居中普通段落 |
| `toc` | `list` | 朴素列表 |
| `gallery` | 逐张 `image` | 逐张 `image` |
| `stats` | `list` | 朴素列表 |
| `timeline` | `list`（有序） | 有序列表 |
| `faq` | `list` | 加粗问 + 段落 |
| `callout` | `quote` | 居中大字段落 |
| `keyvalue` | `table` | 逐行卡片 |
| `video` | `para` | 虚线占位卡 + 原文件名 |
| `audio` | `video` | 虚线占位卡 + 原文件名 |
| `footer` | `para` | 灰色小字段落 |
| `code` | `para` | 浅底等宽段落（**不能用 `<pre>`**） |
| `list` | `para` | 每行一个段落，前缀 `·` |
| `signature` | `cta` | 居右署名行 |
| `image` | —— | 裸 `<img>` + **自动补 `data-w`/`data-ratio`** |
| `divider` | —— | 居中 `···` 段落 |
| `endline` | —— | 居中 `···` 段落 |
| `table` | `list` | 逐行卡片 |
| `para` | —— | 无降级（必须有） |
| `chapter` | —— | `<h2>` 朴素标题 |

> **`compare` 的降级特意写成「两张独立卡片」而不是「拆掉 flex」：**
> 历史上做过一次把 `display:flex` 全改成 `inline-block` 的「修复」，结果十几处排版全崩。
> **教训：宁可牺牲两栏并排，也不要动布局原语。** 已写进踩坑清单的反面案例。

## 6. 模板插值规则

### 6.1 变量作用域（后者覆盖前者）

```js
{ ...theme.tokens, ...theme.base, ...block, ...runtime }
```

`block` 覆盖同名 token，所以模板里可以直接写 `{{title}}` `{{text}}`，不用套层。

### 6.2 两个保留插槽

| 插槽 | 含义 | 是否转义 |
| -- | -- | -- |
| `{{content}}` | 子组件已渲染好的 HTML | **不转义** |
| `{{text}}` | 纯文本 | 转义 `<` 与 `&`（不解析实体） |

### 6.3 `wrap` / `tpl` 双层结构

沿用 `docs/04` 的写法，`wrap` 是外层容器，`tpl` 是内层元素：

```jsonc
"para": {
  "from": "paragraph",
  "wrap": "<section style=\"margin-top:{{paraGap}};font-family:{{fontFamily}};\">{{content}}</section>",
  "tpl":  "<p style=\"margin:0;font-size:{{fontSize}};line-height:{{lineHeight}};text-align:{{align}};color:{{textMain}};\"><span leaf=\"\">{{text}}</span></p>"
}
```

**为什么要有两层**：间距挂在外层 `<section>`（微信对 `<p>` 的默认 margin 行为不可靠），
文字样式挂在内层 `<p>`。这直接从成品反推——57 个模块全部符合这个结构。

### 6.4 硬性要求（否则微信会吃掉）

- 布局只用 `<section>`，**禁止 `<div>`**
- 禁止 `class` / `id` / `<style>` / `<script>`
- 样式全部内联 `style`
- 每个文本叶子必须 `<span leaf="">` 包裹
- 属性顺序建议固定，方便日后 diff

### 6.5 条件段：写残了会静默发生

`{{?key}} … {{/key}}` 必须成对，**端点括号一个都不能少**。
`fill()`（`core.js:38`）只认合法语法，匹配不上就原样输出 —— 不报错、不警告，
残缺标记会直接出现在用户文章里。

> 2026-10-06 实例：作者卡 tpl 写成 `{{?account} … {/account}`，产物多出 53 字符残缺标记。
> 发现方式是拿渲染字节数逐字节比对，不是靠肉眼。

两道机器闸门（详见 `docs/04` §3.1）：

| 闸门 | 检查 | 失败后果 |
| -- | -- | -- |
| `check/build_theme_js.py` | 残缺括号 + 开闭不配对 | **拒绝编译**，不产出 `.js` |
| 体检第 7 片 `模板` | 产物含 `{{?` / `{/x` / `{{x}}` | **禁用复制按钮** + 给出理由 |

对应的指标名是 `metrics().templateResidue`，`node check/test_engine.js` 的 ⑤ 行会打印它。

## 7. 引擎模块划分

```
engine/
├─ modules.js     ★★ 模块注册表 —— 新增组件的唯一入口（见下）
├─ core.js        全局命名空间 / 工具函数（`window.GZH`）
├─ parse.js       md → AST（自研块解析器，零依赖）
├─ ir.js          AST（含 ::: 盒子）→ IR    ★ 实现 §3 §4
├─ render.js      IR + theme → HTML              ★ 实现 §5 §6
├─ sanitize.js    合规后处理 + rules 校验         ★ 实现 §9
├─ clipboard.js   ClipboardItem 直写剪贴板
└─ placeholders.js 三张 base64 占位图（由 check/make_placeholders.py 生成）

themes/
├─ index.json             主题清单（App 扫描它生成下拉，丢个 JSON 进目录就自动出现）
├─ _template.json         空壳模板，新主题从此复制
└─ blue-editorial.json    从 v5 成品倒推的第一套
```

### 7.1 `modules.js` —— 为什么它是唯一入口

历史上加一个组件要动 **9 个文件 33 处**（ir / render / fallback / 主题 JSON /
index.html / docs 04·06·07·08），根因是同一个组件的信息被拆散放在 4 个地方。
现在一个组件的全部信息收在注册表的一条里，下游全是派生出来的：

| 字段 | 说什么 | 谁消费 |
| -- | -- | -- |
| `ui` | 左栏显示名 / 分组 / 插入片段 | `index.html` 遍历生成左栏 |
| `grammar` | Markdown 怎么识别、字段怎么提取 | `ir.js` 查表，不再写 `if (b.name === 'xxx')` |
| `fallback` | 主题没实现时的兜底模板 | 自动拼成 `GZH.FALLBACK` |
| `fallback.source` | 子项从哪个字段取（`items` / `columns`） | `render.js`，替代原来的 role 判断 |
| `grammar.kv` | 盒内 `key: value` 行直接铺成同名字段 | `ir.js` —— 这是「一个盒子装全部」的关键 |
| `grammar.slots` | 哪些字段要过占位图回落 | `ir.js` → `pickSrc` |
| `grammar.derive` | 派生字段（头像首字等） | `ir.js` → `DERIVERS` |

**容器的 IR 流水线**（`ir.js` 固定六步，顺序不可换）：

```
static  写死字段
  ↓
kv      `key: value` 行 → 同名字段
  ↓
map     声明式提取（title / lede / items / columns …）
  ↓
slots   声明的图片字段 → pickSrc 占位回落
  ↓
derive  派生字段（initial ← author）
  ↓
defaults 缺省值（如看点卡默认标签）
```

**加一个新容器组件的完整流程**：在 `MODULES` 里加一条 → 完。
想给它更精细的皮肤，才去主题 JSON 里补一个 `components.<role>`（不补也照常出成品）。

⚠️ `MODULES` 里的书写顺序（篇首 → 篇尾）**就是左栏的显示顺序**，别随意插到中间。
⚠️ `grammar.map` 的遍历顺序有语义：`link` 会把链接从末行删掉，必须排在 `join` 前面。

**依赖方向必须单向**：`parse ← ir ← render ← sanitize`，**禁止反向 import**，
也禁止 `ir.js` 里出现任何颜色值。这条要在 review 时把关。

## 8. 三条入口如何共用

```
人     →  app/index.html  ─┐
大模型 →  产出带扩展标记的 md ─┼→ ir.js → render.js → sanitize.js → clipboard.js → 微信
CLI    →  node cli.js <file> ─┘
```

| 入口 | 提供什么 | 不提供什么 |
| -- | -- | -- |
| **人** | 完整 md（每个盒子自包含：`:::masthead` / `:::profile` / `:::note` …） | —— |
| **大模型** | IR 的文本形式：`:::容器块` + 标准 md | **绝不给最终 HTML** |
| **CLI**（第二阶段） | 同上 + `-t <theme>` `-o <file>` | —— |

### 大模型那条链的边界（**重要**）

**只让模型产出语义层，绝不让模型写最终 HTML。** 理由不是偏好，是实测：

- 让模型逐行手写几万字符 HTML，**同一份稿子今天明天长不一样**
- 长文必然漏写 `<span leaf="">` 叶节点包裹
- `display:flex` 数量不可控 —— 而这是布局塌陷的直接原因
- 换个配色还要整篇重跑一遍模型

模型侧的 prompt 只需交付：「按这份 IR 契约，把这篇稿子组织成若干个 `:::` 盒子」。
每个盒子自带它需要的全部字段，**不要把所有信息塞进文件头 YAML**。
**渲染交给我们。** 这也顺带解决了 token 成本问题。

## 9. 校验闭环（三道）

| 时机 | 做什么 | 工具 |
| -- | -- | -- |
| **渲染后**（内联） | 套 `theme.rules`：渐变配额、`text-align` 白名单、`<img>` 必带尺寸属性 | `sanitize.js` |
| **复制前**（UI） | 体检计数上屏：`flex` 数 / `gradient` 数 / `text-align` 分布。**不达标就禁用复制按钮** | `app.js` |
| **发布后** | 抓已发布链接或导出的 mhtml，比对 browser 计算样式指纹 | `check/check_published.py` |

**三个必须在 UI 上显示并锁定的数字**（来自需求文档的质量红线）：

| 指标 | 目标 | 依据 |
| -- | -- | -- |
| `text-align:start` | **0** | 规范 §1.6 禁用值；曾真实出现 53 处 |
| `text-align:left` | **0** | 已发布零告警对照组实测为 0 |
| `display:flex` | **源文件 = 剪贴板 = 已发布，三处必须相等** | 手动复制会把它抹成 0 |

> 第三条最能救命：**这个数一对不上，100% 是复制链接脏了**，不用怀疑模板。

| 步骤 | 产出 | 验收标准 |
| -- | -- | -- |
| 1 | `parse.js` + `ir.js`（只做 `para`/`chapter`/`quote`/`image`） | `demo.md` 能产出结构化 IR |
