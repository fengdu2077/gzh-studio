# 10 · 重写规划：元素化架构（把「编辑」变成结构上的必然）

> 状态：**已落地**（实现见 `docs/13-元素化架构实现记录.md`）
> 你问：如果重写一次，结局会不会还是卡在「不能编辑元素、无法编辑骨架」？
> 这一篇先回答这个问题，再给架构。

> **更新 2026-10-07**：架构已按这一篇落地完 —— 引擎层换成元素树、UI 换成「点元素改属性」，
> 3 套主题 × 20 个模板全部迁移，**渲染输出与迁移前逐字节一致**（`check/build_compositions.js`
> 每次写入前强制做往返校验，不等就中止）。落地过程中的取舍与踩到的坑记在 `docs/13`。
>
> 与当初设想不同的三点，都是实现中被现实修正的：
> 1. 元素的样式没有拆成 `radius` / `fontSize` 这类固定字段，而是**有序的 CSS 属性字典**
>    （另加 `__order` / `__semi` 保输出顺序）—— 原因是固定字段集装不下现实的 CSS，
>    而「忠于原文」是零回归的前提。详见 docs/13 §2。
> 2. 迁移不是手写 60 棵树，而是写一个**保守的自动翻译器**（`engine/tplparse.js`），
>    译不干净的一律整块保留（当前 17%）。
> 3. 元素树 Md 存的同时，`components.*.tpl` **没有删** —— 它是回归基准和兜底，
>    也让「没带 compositions 的老主题」自动获得元素化编辑能力。

## 一、直接回答：会不会再卡住

**取决于一件事，且只取决于这一件事：原子的存储格式是「属性化的数据」还是「一整段 HTML 字符串」。**

- 如果原子是**属性化的数据**（`{type:'text', fontSize:22, color:'{{accent}}'}`）→ 不会卡。
  字号、颜色、圆角、渐变天然就是一个个字段，UI 直接改字段，没有"读不懂的字符串"这回事。
- 如果原子还是**HTML 字符串**（`"<p style='font-size:22px;color:#4E8FA3'>…"`）→ **一定会再卡住**，
  重写十次也一样。因为你想改的那个 22px 藏在字符串里，程序不知道它是个"字号"，
  也不知道它旁边的 1080 是宽度还是行高。

**现在卡住的根因就是这个**：主题被设计成「模板字符串的集合」，而不是「属性值的集合」。
所以「改字号」= 改字符串；「删封面」= 删字符串里的一段；「新增组件」= 得去代码里注册骨架。
这不是代码写得好不好的问题，是**存储格式选错了**。

重写的意义只有一个：**把存储格式换掉**。换掉之后，"能编辑"是结构上的必然，而不是靠我记着去实现。

## 二、重写后的四层

```
① 语法层   :::card  /  ![]()  /  ## 标题        ← 作者写的，只有语义，零外观
② 元素层   text / box / image / divider / spacer / grid / raw   ← 原子，属性化，可被 UI 逐项改
③ 组合层   card = [ box > [text(标题), text(正文), image({{?cover}})] ]   ← 骨架，属于主题
④ 主题层   tokens(色/尺度) + compositions(骨架) + overrides(默认值)      ← 皮肤 + 骨架，都是数据
              ↓
⑤ 渲染器   元素树 → 微信合规 HTML（全项目唯一一处生成 HTML 的地方）
```

关键变化：**引擎只认 8 种元素，不再认 15 个 role。**
新增组件 = 在主题里加一条 composition，**引擎零改动** —— "无法编辑骨架"这个问题从根上消失。

### 元素（原子，全项目就这么几种）

| type | 管什么 | 可改的属性（UI 直接给控件） |
| -- | -- | -- |
| `text` | 一段文字 | fontSize(px) / fontWeight / color / lineHeight / letterSpacing / align / marginBottom / 上下边框 |
| `box` | 一个盒子（自动渲染成 `<section>`） | bg（可填渐变）/ border(width,color,style) / radius(px) / padding / margin / shadow / 子元素 |
| `image` | 图 | src / radius / width / ratio / marginBottom |
| `divider` | 分隔线 | 样式（细线 / 圆点 / END 字）/ color / 上下留白 |
| `spacer` | 空白 | height(px) |
| `badge` | 小标签（序号、眉标） | text / color / bg / radius / padding / fontSize |
| `grid` | 分栏（受微信 flex 限制，只做等宽 2–3 栏） | cols / gap / 子元素 |
| `raw` | **逃生舱**：塞一段手写 HTML | html 字符串 |

`raw` 必须有 —— 元素库没覆盖到的效果不至于做不出来；但它是逃生舱，不能成为主路径。

### 组合（骨架，写在主题里）

```json
"compositions": {
  "card": {
    "label": "卡片", "icon": "▤",
    "fields": ["title", "text", "cover"],
    "tree": [
      { "type": "box", "bg": "{{cardBg}}", "radius": "{{radius}}",
        "border": { "width": 1, "color": "{{accentTint}}" },
        "padding": [16, 17], "children": [
          { "type": "badge", "text": "{{kicker}}", "color": "{{accent}}" },
          { "type": "text", "text": "{{title}}", "fontSize": 22, "fontWeight": 700, "color": "{{textStrong}}" },
          { "type": "image", "src": "{{cover}}", "radius": "{{radiusSm}}" }
        ] }
    ]
  }
}
```

- `:::card` 只表示「这里用一个叫 card 的组合」，具体由哪些元素构成，**当前主题说了算**。
- 你举的例子天然成立：`card` 在 A 主题的 tree 里有 `image`，B 主题里没有 —— 同一个 `:::card`，
  A 出图 B 不出图。**不需要改代码，改主题数据即可。**
- `image` 的 `src` 是 `{{cover}}`：作者没写 `cover` → 空 → 该元素自动跳过（沿用现有三态规则）。

### 主题 = 色板 + 尺度 + 骨架 + 默认值

```json
{ "tokens": { "accent": "#4E8FA3", "gold": "#E2A341", ... },
  "base":   { "fontSize": 16, "lineHeight": 1.9, "cardGap": 30, ... },
  "compositions": { "card": {...}, "masthead": {...}, "verdict": {...} },
  "elementDefaults": { "box": { "radius": 10 }, "text": { "lineHeight": 1.9 } } }
```

`elementDefaults` 让"所有卡片圆角统一 12px"这种事只改一处。

## 三、四条不变量（写死，防止我下次又把它做回去）

1. **存储格式 ≠ 输出格式**：存的是 JSON 属性树，HTML 只是渲染产物，**永远不从 HTML 反解属性**。
2. **引擎只认有限元素类型**：任何新组件都不得要求改引擎。谁提这个要求，说明元素库缺一种 type，
   应该加 type，而不是加 role。
3. **骨架属于主题，不属于代码**：`:::xxx` 的构成写在主题里；代码里出现任何具体组件名都是设计错误。
4. **任何「用户想改的」必须是数据里的一个字段**：如果它藏在字符串里，就等于用户不能改。
   加功能时先问：这个东西是字段吗？不是就先建模成字段。

## 四、可视化界面（重写后的样子）

三栏不变，中间那栏换成：

| 区 | 内容 |
| -- | -- |
| 左 | 组件列表（主题的 compositions，含你自己造的）+ 「＋ 新建组件」 |
| 中 | 增强 Markdown（照旧写稿）+ 选中某个盒子时，下方弹出**该组合的元素树** |
| 右 | 实时预览（照旧） |

点中元素树里任一节点 → 右侧**属性面板**：

- 文字：字号(数字+滑块) / 粗细(下拉) / 颜色(取色器 + token 下拉) / 行高 / 字距 / 对齐
- 盒子：底色(纯色 / **渐变编辑器**：两色 + 角度，自动避开微信 135° 限制) / 边框(粗细+颜色+实虚) /
  圆角(数字) / 内距 / 外距 / 阴影(开关 + 强度)
- 图片：圆角 / 宽度 / 比例
- 每个属性旁边一个「跟着 token」开关：勾上就写 `{{accent}}`，换主色它自己变；不勾就是字面量

改完 → 存回当前主题（或另存为新主题）→ 导出仍是全量快照 `.js`。

**新增组件**：起名字 → 选起点（空白 / 复制某个现有组合）→ 在元素树上加节点 → 改属性 → 保存。
全程不出现 HTML。

## 五、迁移：不推倒重来，长出新的一层

现有 3 套主题 + 15 个组件 + 已验证的微信合规规则是资产，不丢。

| 阶段 | 做什么 | 风险 |
| -- | -- | -- |
| 1 | 新建 `engine/elements.js`（元素库）+ `engine/compose.js`（元素树→HTML）；现有 `render.js` 不动 | 无（新增文件） |
| 2 | 现有 15 个 `components.*.tpl` 整体包成 `raw` 元素 → **输出逐字节不变** | 零，用来做回归基线 |
| 3 | 逐个把 tpl 翻译成元素树（先刊头卡 / 卡片 / 引述 / 结论卡这 4 个最高频的） | 每翻译一个跑一次字节对比 |
| 4 | 属性面板 + 组合编辑器上线，主题 JSON 开始带 `compositions` | 中 |
| 5 | 剩余组件翻译完；`raw` 只留给真正特殊的 | 低 |

**回滚成本**：阶段 2 之后随时可以只用老路径，两条渲染链并存，由主题里有没有 `compositions` 决定走哪条。

## 六、工作量与风险（不夸大）

| 项 | 估 |
| -- | -- |
| 元素库 + 元素渲染器（8 种 type + 微信合规内建） | 1 天 |
| 组合层 + 与现有 IR 对接 | 半天 |
| 属性面板 + 渐变编辑器 + 组件树 UI | 1 天 |
| 3 套主题 × 15 组件翻译成元素树 | 1–2 天（可分批，先 4 个高频的） |
| 测试与回归（字节对比 + 合规体检） | 半天 |
| **合计** | **3–5 天**，分批交付，每批都能用 |

风险：
- **元素库漏一种效果** → 用 `raw` 逃生舱兜底，不会做不出来，只是那个组件暂时还得看 HTML
- **微信 flex 支持有限** → `grid` 只做等宽 2–3 栏，更复杂的用图片代替
- **渐变限制**（135° 与总数）→ 渲染器内建计数与告警，属性面板直接拦住
- **翻译期两套并存** → 主题里有没有 `compositions` 决定走哪条链，互不干扰

## 七、验收（这次按你能做到什么来验收）

1. 你新建一个组件（比如 `:::verdict`），全程不碰 HTML
2. 你把某个卡片的圆角从 10px 改成 0、底色从纯色改成渐变、去掉阴影 —— 三个都点几下就完成
3. 同一个 `:::card`，在 A 主题有图、B 主题没图 —— 只改主题数据
4. 把正文字号从 16px 改成 15px，全篇跟着变
5. 导出主题给朋友，他导入后这些组件和改动都在
6. 原有测试全绿 + 阶段 2 的字节对比零差异
